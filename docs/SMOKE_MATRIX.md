# 可视化验收用例

把接口层与跨层组合的 **131 个测试点**拆成可以照着点的用例。判据一律是**肉眼看得见的画面**，不是 DOM 属性 —— 所以同一份文档，人能照着点，浏览器智能体也能照着点。

它和别的文档的分工：`docs/WEB_UI_MAP.md` 说页面有哪些区域，`docs/CAPABILITY_MATRIX.md` 说能力的条件与边界，`docs/TESTING.md` 的 TC-\* 是人工验收断言。这份补的是**「怎么一步步点，以及凭什么算通过」**。

## 怎么用这份文档

两种后端都能跑，先选一种：

| | mock（推荐日常回归） | 真实 Codex |
|---|---|---|
| 启动 | `node scripts/mock-server.js` | `npm start` |
| 地址 | `http://localhost:3232` | `http://127.0.0.1:3001` |
| 认证 | 无 | 需 `AUTH_TOKEN`；置空则仅 loopback 可进 |
| 额度 | 零 | 每轮真实对话都消耗 |
| 触发方式 | 固定剧本关键词 | 自然语言指令 |

每条用例的「步骤」里，需要输入内容的地方同时给出两种：`mock：XXX_FIXTURE` / `真实：某句话`。mock 的全部剧本关键词见 `scripts/mock-codex-app-server.js`：`SLOW_TURN`、`FILE_CHANGE_FIXTURE`、`MARKDOWN_FIXTURE`、`RICH_MARKDOWN_FIXTURE`、`REASONING_STREAM_FIXTURE`、`TURN_GROUP_FIXTURE`、`SCROLL_STREAM_FIXTURE`、`PRE_ACK_STREAM`、`approve`。

### mock 验不了什么

mock 只替换了 Codex 进程，`fs/*`、`git/*`、`account/*`、`mcp/*`、`skills/*` 这些请求它一律回空对象。下面这些用例在 mock 上**必然看到空态或触发不出来**，那不是缺陷，是选错了后端：

| 用例 | mock 上的表现 | 原因 |
|---|---|---|
| VC-F12 工作区文件浏览 | 文件列表**永远是空的** | mock 不实现 `fs/readDirectory`、`fs/readFile` |
| VC-F13 git 改动与 diff | 改动列表**永远是空的** | mock 的工作区是临时目录，根本不是 git 仓库 |
| VC-E01 的代码块部分 | 没有围栏代码块 | 所有剧本里都只有行内 code |
| VC-E04 / E05 / E06 | 不产生 plan / turn diff / 搜索卡 | mock 无对应剧本 |
| VC-E07 MCP 工具卡 | 面板空态 | `mcp:read` 回空 |
| VC-E10 的多数行 | 触发不出来 | `account/*`、`skills/*`、`externalAgentConfig/*` 全回空 |
| VC-D06 提问卡 | 触发不出来 | mock 不产生 `user_input_request` |
| VC-D09 非零退出码 | 永远 `exit: 0` | mock 的命令固定成功 |

**这些一律用真实后端跑。** 在 mock 上看到空态就记「后端不支持」，不要记失败。

**给人**：从第 0 幕顺着往下走，一幕就是一段连贯的使用旅程，不用跳。

**给浏览器智能体**：每条用例末尾的「定位参考」给出 selector。注意三个实测踩过的坑：

1. **读文字用 `textContent`，不要用 `innerText`。** 消息刚渲染完时布局未完成，`innerText` 会返回空串，导致断言假失败。
2. **列表要轮询等，不要用固定延时。** 抽屉首次打开时 thread 列表还在路上，等 700ms 会拿到 0 行。
3. **点击和滚动可能都要降级。** 实测遇到过 CDP 的 `Input.dispatchMouseEvent` 连续 30 秒超时，`scroll` 也静默失效（不报错但页面不动），而**键盘事件和 JS 执行完全正常**。降级方案：点击用 `element.click()`，滚动用 `el.scrollTop = el.scrollHeight`。它们走同一个事件处理器，**但验证不了遮挡、`pointer-events` 和 hit-testing** —— 用了降级就在报告里标注，别当成验证过可点击性。
4. **刚 navigate 完别立刻打字。** 页面重建视图期间输入会被丢掉，看起来像"发送失败"。先轮询确认输入框已聚焦且能接收内容，再按回车。

## 一条用例怎么读

- **覆盖点** —— 这条用例验证了 131 个点中的哪几个，用于附录 A 的追溯。
- **前置** —— 不满足就不用往下走，结果无意义。
- **步骤** —— 人能照做的动作描述。位置用「输入框右侧」这种说法，不用 selector。
- **看到什么** —— 按**时机 × 画面变化**列表。视觉验证的本质是看**变化**，不是看静态状态，所以逐格核对。
- **判定** —— ✅ 是通过的充分条件，❌ 是最容易误判成通过的那种情况。
- **定位参考** —— 只给自动化用。**它不是判据**：判据永远是上面那张画面表。

参数化用例（如审批×沙箱、离线×outbox 状态）在正文后跟一张参数表，逐行重复执行同一套步骤。

### 状态怎么用眼睛看

页面里那个 `idle` / `running` 文本是**给屏幕阅读器用的**，它被压成 1×1 像素并裁剪掉，**视觉上完全看不见** —— 别拿它当判据。肉眼能看到的状态信号只有这三处：

| 信号 | 位置 | 含义 |
|---|---|---|
| 小圆点**绿色、不闪** | 左上角抽屉按钮右下 | 已连接、空闲 |
| 小圆点**橙黄色、持续闪烁** | 同上 | 正在跑一轮 |
| 小圆点**橙色、持续闪烁** | 同上 | 在等你审批 |
| 小圆点**灰色、无光晕** | 同上 | 已断开 |
| 右下角**实心方块**（而非箭头） | 输入框右下 | 正在跑，可点它停止 |
| **转圈动画** | 输入框右侧、回形针左边 | 正在跑 |

## 贯穿所有用例的判据

下面两条**不属于任何单条用例，而是每条用例都要顺手看一眼**。它们各自对应一次真实事故，而且都是纯肉眼可见的 —— 正因为不属于任何一条，才最容易全程没人看。

**1. 界面上任何位置都不得出现宿主机绝对路径。**

错误提示、命令卡、附件条、系统消息条 —— 只要看到 `/Users/…`、`/home/…`、`C:\Users\…` 这种完整路径，就记失败，写清楚哪条用例、哪个位置。

- 为什么要盯：服务端有 11 处把异常文案原样送去浏览器。手机可能正连在公网上，报错里的绝对路径会连带暴露宿主机用户名和目录结构。这些点现在统一走脱敏，但**脱敏是一层容易被绕开的收敛** —— 新加一处 `` `…${err.message}` `` 就漏了。
- ✅ 报错说清楚发生了什么，路径部分是文件名或相对路径
- ❌ 出现完整绝对路径 —— 哪怕报错本身是对的

**2. 同一类错误提示不得堆积刷屏。**

- 为什么要盯：VC-G01 实测抓到过断线期间「连接失败」红条 45 秒堆 9 条，把对话整个挤出视野。修了，但任何新的错误通道都可能重犯。
- ✅ 同类提示合并或替换，对话内容始终可见
- ❌ 提示条不断累积，需要滚动才能看到消息

## 第 0 幕 · 打开与连接

#### VC-A01 · 口令登录门

**覆盖点** `POST /auth/session` · `#auth-gate` 渲染

**前置** `.env` 里 `AUTH_TOKEN` 已设为非空值，服务已重启

**步骤**
1. 浏览器打开服务地址
2. 在中间那个输入框里故意输错一个口令，点「连接」
3. 清空，输入 `.env` 里真实的 `AUTH_TOKEN`，点「连接」

**看到什么**
| 时机 | 画面变化 |
|---|---|
| 刚打开 | 整页只有一个居中的卡片，标题「输入访问口令」，下面一个输入框和一个黑色「连接」按钮，看不到聊天界面 |
| 打字时 | 输入内容**以圆点掩码显示**，不是明文 |
| 输错后 | 按钮下方出现提示「访问口令不正确，请重试。」，仍停在这一页 |
| 输对后 | 卡片整个消失，露出聊天主界面：顶栏、消息区、底部输入框 |

**判定**
- ✅ 口令以掩码输入；错误口令留在原页并给出可见提示；正确口令后主界面完整出现
- ❌ 输错后直接进了主界面 —— 认证形同虚设
- ❌ 口令以明文显示 —— 肩窥风险

> 💡 **错误路径可以自动化**（随便输一个错的字符串不算凭据），只有"输入真实口令"那一步必须人来。

**定位参考** `#auth-gate` · `#auth-token-input` · `#auth-submit` · `#auth-error`

> ⚠️ **仅限手工**。凭据输入不交给自动化执行。

#### VC-A02 · 设备配对等待与批准

**覆盖点** `device_status` · `pending_devices` · `user:approveDevice` · `user:denyDevice`

**前置** 一台机器就够，**不需要第二台真机**。要的是「两个 origin，其中一个非 loopback」，服务端按下面四项配齐后重启：

| 配置 | 值 | 少了会怎样 |
|---|---|---|
| `HOST` | `0.0.0.0` | 只监听 loopback，远程根本连不上 |
| `AUTH_TOKEN` | ≥32 字符 | 启动即报错，拒绝绑定远程网卡 |
| `CODEX_ALLOW_INSECURE_REMOTE` | `1` | 明文 HTTP 的远程请求收 **426 `https_required`**，到不了配对画面 |
| `CODEX_ALLOWED_ORIGINS` | `http://<本机局域网 IP>:<PORT>` | socket 握手收 **403 `origin_not_allowed`** |

> ⚠️ 后两项**只在本机验收时开**，等价于自愿放弃传输层加密，绝不能留在真实部署里。`SECURITY.md` 的部署规则以那边为准。
>
> 早先这里写的是「需要第二台设备」。那是错的，而且错得很贵：真搬第二台设备来、走明文 HTTP，一样是 426，于是连着两轮被记成「跑不了」而整条跳过 —— **这是本文档唯一一条用肉眼守设备闸的用例**。设备数量从来不是障碍，传输层才是。

**步骤**
1. 用 `http://127.0.0.1:<PORT>` 打开一个窗口，通过口令 —— 这是**已信任**的那一端（A）
2. **同一个浏览器**里另开一个标签页，用 `http://<局域网 IP>:<PORT>` 打开 —— 这是**待批**的那一端（B）。不用无痕、不用第二个浏览器配置：设备标识存在 `localStorage`，而 localStorage 按 origin 隔离，换个 origin 就自动是另一台设备
3. 回到 A 看页面顶部
4. 在 A 上点「批准」
5. 观察 B

**看到什么**
| 时机 | 画面变化 |
|---|---|
| 第二台设备刚连上 | 它自己停在一个等待画面，显示本机设备号，进不去聊天界面 |
| 同时在第一台设备 | 顶部出现一条待批设备提示，带设备信息和「批准」「拒绝」两个按钮 |
| 点批准后 | 第一台设备的提示条消失；第二台设备**自动**进入聊天主界面，无需刷新 |
| 若改点拒绝 | 第二台设备被断开，退回等待或口令画面 |

**判定**
- ✅ 未批准前 B **看不到任何聊天内容**；批准后自动放行
- ❌ B 在批准前就能看到消息、命令卡或工作区路径 —— 设备闸没生效

> 💡 这条 ❌ 对应服务端五处 `deviceApproved !== true` 广播闸（`server.js` 的 1196 / 1212 / 1338 / 1383 / 2951 行）。它们有单测守着，而这条用例是**唯一的肉眼版本** —— 单测证明「代码里有这个判断」，只有这里能证明「用户真的什么都看不到」。

**定位参考** `#device-auth` · `#device-id-display` · `#pending-panel` · `.approve-btn[data-id]`

#### VC-A04 · 断线横幅与自动重连

**覆盖点** `status`(断线) · 连接状态维度：在线 → 离线 → 重连

**前置** 页面已连上

**步骤**
1. 停掉服务端进程（或在开发者工具里切到离线）
2. 等约 5 秒

**看到什么**

**判定**
- ✅ 断开有明确可见提示，恢复后提示自动消失，无需刷新
- ❌ 断开后界面毫无变化 —— 用户不知道自己已经离线

## 第 1 幕 · 发一条消息

#### VC-B01 · 文本发送与流式渲染

**覆盖点** `user:message` · `text_delta` · `result` · `user_message`

**前置** 在任意会话里，顶栏小圆点是绿色静止状态

**步骤**
1. 点底部输入框，输入 `mock：你好` / `真实：只回复一个词：PONG`
2. 按回车
3. 一直看着消息区，直到左上角小圆点变回绿色静止

**看到什么**
| 时机 | 画面变化 |
|---|---|
| 回车瞬间 | 输入框清空；消息区**右侧**多出一个浅色气泡，内容是你刚输入的字 |
| 随后 | 消息区**左侧**开始出现回复文字，且是**逐字/逐段冒出来**的，不是一次性整块出现 |
| 完成后 | 小圆点变回**绿色静止**；右下角按钮从方块变回箭头；转圈动画消失 |

**判定**
- ✅ 用户气泡靠右、回复靠左，回复过程肉眼可见是渐进的
- ❌ 回复一次性整块出现 —— 流式没生效（或后端一次性返回）

**定位参考** `#msg-input` · `.msg.user` · `.msg.codex` · `#state-label`

#### VC-B02 · 送达状态标记

**覆盖点** `message_receipt`

**前置** 同上

**步骤**
1. 正常发一条消息
2. 紧盯**刚发出的那个用户气泡**下沿

**看到什么**
| 时机 | 画面变化 |
|---|---|
| 刚发出 | 气泡下方**可能**短暂出现一行小字（排队/等待同步之类） |
| 服务端确认后 | 那行小字消失，气泡变成普通样式 |
| 网络很快时 | 小字一闪而过，**甚至完全来不及出现** —— 这是正常的 |

**判定**
- ✅ 消息发出几秒后，气泡上**最终没有任何等待类小字**（无论中途出没出现过）
- ❌ 小字一直挂着不消失 —— 回执没回来，消息可能没真正送达

> 💡 本机直连时回执往往在一次渲染内就回来了，实测**小字一次都没出现过**。**不要把"没看到小字"判为失败** —— 这条用例真正要守的是"小字不会永久挂着"。要观察到它，得先制造弱网（见 VC-G01）。

**定位参考** `.msg.user .queued-label` · `.msg.user .offline-label`

#### VC-B03 · 运行中追加指令，不另起一轮

**覆盖点** `user:message`(steer) · `queued_message` · `dequeued_message`

**前置** 顶栏小圆点是绿色静止状态

**步骤**
1. 输入 `mock：SLOW_TURN` / `真实：逐个枚举 public/js 下每个文件的职责，每个至少三句话，不要跑命令`，回车
2. 等顶栏小圆点变成橙黄色并开始闪烁
3. **趁回复还在往外冒的时候**，在输入框再输入「补充：只说 outbox 相关的」，**先别回车**
4. 立刻点输入框右侧新冒出来的那个小按钮（在回形针左边，方块的左边）

> ⚠️ **必须抢在这一轮跑完之前**。轮次一旦结束，同样的操作会变成"新起一轮"——那是合理行为，不是缺陷，但这条用例就没验到 steer。真实后端下第一句回复出来得很快，动作要快。

**看到什么**
| 时机 | 画面变化 |
|---|---|
| 步骤 2 后 | 右下角发送箭头变成**实心方块**；输入框附近出现转圈动画 |

**判定**

- ❌ 丢弃了但后面的消息仍卡着 —— 阻塞没解除

**定位参考** `.outbox-discard-btn` · `#confirm-modal` · `#confirm-ok[data-danger]`

#### VC-G05 · 刷新后历史重建

**覆盖点** `catch-up` · `thread_event` · `thread:history`

**前置** 当前会话已有若干轮对话，其中**包含至少一次命令执行**

**步骤**
1. 记下刷新前消息区里有多少个气泡、多少张卡片
2. 刷新整个页面
3. 等加载完，重新数一遍

**看到什么**
| 时机 | 画面变化 |
|---|---|
| 刷新后 | 顶栏标题仍是同一个会话 |
| 消息区 | 用户消息和回复文字**都回来了**，Markdown 排版也正常 |
| 但是 | **命令卡、审批卡、退出码不会回来** |

**判定**
- ✅ 文字类内容完整重建，会话没串到别的
- ❌ 连文字都没了，或串到了别的会话

> ⚠️ 工具卡丢失**不是缺陷**，是上游限制，见附录 C。别重复上报。

**定位参考** `#thread-title` · `.msg.user` · `.msg.codex` · `.tool-card`

#### VC-G06 · 确认对话框的通用形态

**覆盖点** 确认框渲染 · 危险操作拦截

**前置** 任意一个会弹确认的操作（丢弃记录 / 删除会话 / 确认重试）

**步骤**
1. 触发该操作
2. 先点「取消」
3. 再触发一次，这次点「确定」

**看到什么**
| 时机 | 画面变化 |
|---|---|
| 弹出时 | 底部升起一个面板，有标题、一段说明正文、「取消」「确定」两个按钮 |
| 危险操作 | 「确定」按钮是**红色系**，与普通确认区分得开 |
| 点取消 | 面板消失，**什么都没发生** |
| 点确定 | 面板消失，操作执行 |

**判定**
- ✅ 取消真的什么都不做；危险操作的确定键在颜色上有警示
- ❌ 点取消后操作照样执行了 —— 最危险的交互缺陷

**定位参考** `#confirm-modal` · `#confirm-title` · `#confirm-body` · `#confirm-cancel` · `#confirm-ok[data-danger]`

#### VC-G07 · 长时间断线后的增量恢复

**覆盖点** `catch-up` 增量续传 · 连接状态维度

**前置** 一轮长任务正在进行

**步骤**
1. 发起一个长输出任务
2. 在输出**进行到一半时**切断网络
3. 等 10 秒以上
4. 恢复网络

**看到什么**
| 时机 | 画面变化 |
|---|---|
| 断网时 | 输出停住；小圆点转灰；横幅出现 |
| 恢复后 | 横幅消失；**断网期间产生的内容补上来**，接在断点之后 |
| 全程 | 内容**不重复、不缺段** |

**判定**
- ✅ 断点前后内容连续，没有重复段落
- ❌ 出现重复内容，或中间缺了一大块

**定位参考** `#conn-banner` · `.msg.codex` · `#state-label`

## 第 7 幕 · 多设备

这一幕都需要**两个浏览器窗口**（或两台设备）同时打开同一个服务地址。下称窗口 A、窗口 B。

#### VC-H01 · 同一会话在两端同步

**覆盖点** 多设备维度 · 事件广播

**前置** A、B 都打开**同一个会话**

**步骤**
1. 在 A 里发一条消息
2. 立刻看 B

**看到什么**
| 时机 | 画面变化 |
|---|---|
| A 发送后 | B 的消息区**自动**出现同样的用户气泡，无需刷新 |
| 回复流式时 | B 同步看到回复逐步出现 |
| 完成后 | 两边内容一致 |

**判定**
- ✅ B 无需任何操作即可看到全过程
- ❌ B 要刷新才看得到 —— 实时同步失效

**定位参考** `.msg.user` · `.msg.codex`

#### VC-H02 · 不同会话之间零串流

**覆盖点** 多设备维度 · 事件路由隔离

**前置** A 打开会话甲，B 打开**另一个**会话乙

**步骤**
1. 在 A（会话甲）里发一条消息并等回复
2. 全程盯着 B（会话乙）

**看到什么**
| 时机 | 画面变化 |
|---|---|
| A 对话全程 | B 的消息区**一个字都不应该多出来** |
| B 的圆点 | 保持绿色静止，不受 A 影响 |
| 例外 | B 顶部可能出现「需要你」提示（那是**有意的**跨会话待办聚合，不算串流） |

**判定**
- ✅ B 的消息区完全不受影响
- ❌ 甲的回复出现在乙里 —— 严重的会话串流

**定位参考** `#messages` · `#state-label`

#### VC-H03 · 审批在一端处理后另一端撤销

**覆盖点** `approval_revoked` · 多设备维度

**前置** A、B 都打开同一会话，且有一个审批正挂着

**步骤**
1. 确认两边都能看到审批卡和按钮
2. 在 A 点「批准」
3. 立刻看 B

**看到什么**
| 时机 | 画面变化 |
|---|---|
| 处理前 | A、B 两边都显示审批卡和两个按钮 |
| A 处理后 | B 的按钮**自行消失**，卡片转为已处理 |
| 两边顶部 | 「需要你」计数同时归零 |

**判定**
- ✅ B 在 A 处理后失去再次决议的机会
- ❌ B 仍能点批准 —— 同一审批可能被决议两次

**定位参考** `.approve-btn` · `.deny-btn` · `#needs-you-panel`

#### VC-H04 · 忙闲状态跨端同步

**覆盖点** `thread_status` · 多设备维度

**前置** A、B 都打开抽屉，能看到同一个会话行

**步骤**
1. 在 A 里对该会话发起一轮长任务
2. 看 B 抽屉里那一行的小圆点

**看到什么**
| 时机 | 画面变化 |
|---|---|
| A 开始跑 | B 抽屉里该会话行的圆点变成"进行中"色 |
| A 完成后 | B 的圆点变回空闲色 |

**判定**
- ✅ B 无需刷新即可看出该会话正忙
- ❌ B 的圆点始终不变 —— 跨端状态不同步

**定位参考** `.session-item .thread-status-dot`

#### VC-H05 · 撤销设备后立即失效

**覆盖点** `device_status` · `user:denyDevice` · 多设备维度

**前置** 同 VC-A02 的四项服务端配置（`HOST` / `AUTH_TOKEN` / `CODEX_ALLOW_INSECURE_REMOTE` / `CODEX_ALLOWED_ORIGINS`），且 B 那一端（局域网 origin）已跑完 VC-A02 被批准。同样**一台机器两个标签页**即可。

**步骤**
1. 在 A 上找到设备管理入口，撤销 B 的授权
2. 立刻在 B 上尝试发一条消息

**看到什么**
| 时机 | 画面变化 |
|---|---|
| 撤销后 | B **立即**被踢出，退回等待或口令画面 |
| B 尝试操作 | 发不出去，看不到新内容 |
| 无需刷新 | 失效是即时的，不是等到下次刷新 |

**判定**
- ✅ 撤销即时生效，B 立刻失去访问
- ❌ B 还能继续用直到刷新 —— 撤销有窗口期

> ⚠️ **仅限手工**：撤销入口的确认交互不交给自动化。

**定位参考** `#device-auth` · `#pending-panel`

## 条件可达与不可达

#### VC-J01 · Web Push 订阅

**覆盖点** `POST /push/subscribe` · 订阅入口条件显示

**前置** 需**真** HTTPS + 配齐 VAPID 三项 + 设备已批准

> ⚠️ VC-A02 那套 `CODEX_ALLOW_INSECURE_REMOTE=1` 对这条**不管用**。那个开关放行的是服务端的传输层检查，而 Push API 要的是**浏览器侧的 secure context** —— 浏览器自己拒绝在明文 HTTP 页面上暴露 `PushManager`，服务端说什么都没用。唯一出路是真证书（自签 + 手工信任，或 `docs/REMOTE_ACCESS.md` 里的隧道方案）。loopback 是 secure context，但 loopback 上又没有远程设备可订阅。

**步骤**
1. 未配 VAPID 时打开抽屉，找订阅按钮
2. 配齐后再看

**看到什么**
| 时机 | 画面变化 |
|---|---|
| 未配置 | 抽屉里**看不到**订阅入口 |
| 配齐 + HTTPS | 抽屉里出现订阅按钮，可点 |
| 点击后 | 浏览器弹出通知权限询问；允许后按钮转为已订阅状态 |

**判定**
- ✅ 条件不满足时入口不出现，满足时可完成订阅
- ❌ 条件不满足却显示了按钮，点了报错

> ⚠️ 需 HTTPS，**仅限手工**。

**定位参考** `#push-subscribe-btn`

**覆盖点** manifest · Service Worker 注册

**前置** HTTPS 或 localhost

**看到什么**

| 安装后打开 | 以**独立窗口**运行，没有浏览器地址栏 |
| 图标 | 应用图标和名称正确显示 |

**判定**
- ✅ 能装成独立应用且外观正确
- ❌ 装完打开还是普通网页样式

> 💡 Service Worker 只负责推送通知，**不提供离线缓存** —— 断网后打开应用是白屏，这是设计如此，不是缺陷。

**定位参考** `/manifest.webmanifest` · `navigator.serviceWorker`

- ❌ 能看到并且能点 —— 实验功能泄漏到默认界面

## 第 8 幕 · iOS 真机

**这一幕不增加测试点，增加的是执行环境。** 前面所有用例都跑在 Chromium 或 WebKit 上；这四条只能在真 iPhone 上跑。

`playwright.config.js` 有一条 `mobile-webkit` project，它比 Firefox 更接近 iPhone，能抓布局回归和 CSS 兼容——**但抓不到下面这些**：PWA 的安装路径、真实推送授权、软键盘几何、Safari 的存储驱逐。这些依赖操作系统而不是渲染引擎，自动化里没有等价物。

所以它们是人工用例，不是"还没自动化的债"。

**贯穿本幕的前置**：一台 iPhone（iOS 16.4 或更高）· Safari · 网关经 HTTPS 暴露（自签证书需先在设备上信任，否则 Safari 直接拒绝，症状是白屏而非报错）。

#### VC-L01 · 添加到主屏幕

**覆盖点** PWA manifest · iOS standalone 模式

**前置** 见本幕前置。iOS 没有地址栏安装图标，路径与 Chrome 完全不同。

**步骤**
1. Safari 打开网关地址并登录
2. 点底部分享按钮 → 下滑找到「添加到主屏幕」→ 确认
3. 回到主屏，点新出现的图标打开

**看到什么**
| 时机 | 画面变化 |
|---|---|
| 添加时 | 预览里显示应用图标和名称，不是网页截图缩略图 |
| 主屏上 | 图标清晰、名称正确，不是 Safari 的默认书签样式 |
| 打开后 | 全屏独立运行，**顶部没有地址栏、底部没有 Safari 工具栏** |

**判定**
- ✅ 从主屏打开后是独立应用外观
- ❌ 打开后仍带 Safari 地址栏和工具栏（说明 manifest 的 `display` 没生效）

**定位参考** `/manifest.webmanifest` 的 `display: standalone` · `apple-touch-icon`

#### VC-L02 · 推送只在主屏应用里可订阅

**覆盖点** Web Push · iOS 的 standalone 限制

**前置** VC-L01 已完成（**必须先添加到主屏，这是 iOS 的硬限制**）· 服务端 VAPID 三项配齐 · 设备已批准

**步骤**
1. 先在 **Safari 标签页**里打开网关，尝试开启通知
2. 再从**主屏图标**打开，尝试开启通知
3. 在电脑上触发一次需要审批的操作

**看到什么**
| 场景 | 画面变化 |
|---|---|
| Safari 标签页里 | 通知开关不可用，或点击后给出明确说明（不是静默无反应） |
| 主屏应用里 | 弹出系统授权弹窗，允许后开关变为已开启 |
| 触发审批后 | 锁屏或通知中心出现通知，正文**不含命令原文**，点击后直接进入对应会话 |

**判定**
- ✅ 两种场景表现不同且都有明确提示；通知正文已脱敏
- ❌ 标签页里点了没反应也没说明 —— 用户会以为是产品坏了

**定位参考** `POST /push/subscribe` · `navigator.standalone` · `public/js/sw.js`

#### VC-L03 · 软键盘弹起时输入区不被顶出视口

**覆盖点** 移动视口 · 软键盘几何

**前置** 见本幕前置，已连接并进入任一会话

**步骤**
1. 竖屏下点输入框，等软键盘完全弹起
2. 输入几行文字直到输入框长高
3. 转横屏，再点一次输入框
4. 收起键盘

**看到什么**
| 场景 | 画面变化 |
|---|---|
| 竖屏 + 键盘 | 输入框和发送键**都在键盘上方可见**，不被遮住 |
| 多行输入 | 输入框长高时消息区相应压缩，发送键始终可见 |
| 横屏 + 键盘 | 同上；输入区不被顶出屏幕外 |
| 收起键盘 | 布局恢复，没有残留的空白条 |

**判定**
- ✅ 四种情形下发送键都可见可点
- ❌ 任一情形下发送键被遮住或需要滚动才能找到

> 💡 这条在桌面浏览器和 WebKit 模拟里都验不出来：iOS 的 `100vh` 包含地址栏高度，键盘弹起时视口变化的方式与桌面不同。

**定位参考** `#composer` · `#send-btn` · CSS 的 `dvh` / `visualViewport`

#### VC-L04 · 未发出的消息跨应用重启保留

**覆盖点** 离线队列持久化 · Safari 存储行为

**前置** 见本幕前置。需要能切飞行模式。

**步骤**
1. 开飞行模式，在会话里发一条消息
2. 从后台**完全划掉**应用（不是切后台）
3. 重新打开应用
4. 关飞行模式，等重连

**看到什么**
| 时机 | 画面变化 |
|---|---|
| 断网发送后 | 消息出现在对话里，带**未送达**标记 |
| 重开应用后 | 那条消息**仍在**，仍带未送达标记 |
| 恢复网络后 | 标记转为已送达，助手开始回复 |
| 检查对话 | 那条消息**只出现一次**，没有重复 |

**判定**
- ✅ 消息不丢不重，状态标记随网络恢复而变化
- ❌ 重开后消息消失（本地队列被清掉），或恢复网络后发出了两条

> 💡 Safari 在存储压力下会主动清理站点数据。若本条失败，先确认是不是设备存储将满 —— 那是系统行为，不是产品缺陷，但产品应当在消息丢失时给出提示而不是静默。

**定位参考** `public/js/indexeddb-outbox.js` · `public/js/message-outbox.js`

## 附录 C · 上游限制

以下三条**不是本项目的缺陷**，客户端改不了。执行用例时遇到，按预期处理，不要重复上报。

1. **刷新后工具卡不重建。** `thread/read` 即使请求完整视图，也只返回用户消息、回复文字和文件变更三类，从不返回命令执行与推理条目。所以 VC-G05 里命令卡、审批卡、退出码不会回来 —— 文字回来了就算通过。

2. **「对话 / 计划」模式不会真正下发。** `thread/settings/update` 不在稳定协议里，当前 codex-cli 要求完整的会话设置对象，而读取接口并不返回这个对象，客户端无从构造。因此 VC-C04 里模式切换**只改本地显示**，该调用会被判为"形态不受支持"并静默降级，不再弹红错误。

3. **推理内容不下发。** 真实后端送来的推理条目摘要和正文都是空的。所以 VC-E02 在真实后端下的正确画面是"这块区域什么都没有" —— 既没有推理卡，也不该有兜底的 Raw 卡。

**修复后 VC-A02 全条通过**，含核心安全判据：

- ✅ B 停在整屏「等待设备授权」，只显示自己的设备号

### 执行中修正的判据（这份文档自己的问题）

跑之前写的判据里有 20 处站不住，实测时逐条改掉了。最典型的三个：

1. **拿 `idle` / `running` 当视觉判据** —— 那个文本是 1×1 像素、被 clip 裁掉的**屏幕阅读器专用元素**，肉眼根本看不见。11 处全部换成圆点颜色与闪烁。
2. **拿圆点区分 steer 和新起一轮** —— 两轮之间的空隙短到捕捉不到，圆点一直是橙黄。真正的可见证据是那条「**已向当前运行任务追加指令**」提示。
3. **拿"小字出现过再消失"判送达** —— 本机直连时回执在一次渲染内就回来，小字**一次都没出现过**。改成"最终没有残留小字"。

4. **把「绕过批准和沙箱」当成第四档沙箱** —— 光看面板截图，它就排在沙箱三项下面，于是我把参数表从 12 行改成了 16 行。读代码才发现它是个**快捷方式**：点一下等于同时设「从不询问」+「完全访问」，也就是原表的第 12 格。已改回 12 行。

5. **把「跑不起来」当成「需要第二台真机」**（2026-09-02 复核补记）。VC-A02 / VC-H05 连着两轮被整条跳过，理由记的是缺硬件。实测下来真正的障碍是**传输层**：非 loopback 的明文 HTTP 请求收 426 `https_required`，在任何设备逻辑之前就被挡掉 —— **搬第二台设备来也一样进不去**。配齐 `CODEX_ALLOW_INSECURE_REMOTE=1` 和 `CODEX_ALLOWED_ORIGINS` 之后，同一台机器两个标签页（loopback + 局域网 IP，localStorage 按 origin 隔离，天然是两台设备）就跑得通：loopback 那端收到 `init` 和 `pending_devices`，局域网那端只收到 `device_status`。前置已改写，配方本身由 `test/server-security.test.mjs` 守着。

前三条的教训是同一个：**能从 DOM 里读到，不等于用户看得见**。第四条是它的反面：**看得见，不等于看懂了它是什么** —— 视觉验证能确认"有这个控件"，确认不了"它背后是一个维度还是一个快捷键"，那得靠代码。

第五条是另一类，也是最贵的一类：**跳过理由从来没人复核**。判据写错了会在执行时暴露，跳过理由写错了不会 —— 它恰好让人不去执行，于是永远没有机会被发现。这份文档已经如实记了「不可视验证」（附录 B）和「上游限制」（附录 C），但缺一类：**可验证、却从没跑起来过**。那才是真盲区，而它伪装成一行看起来很合理的前置。

> 这条教训在写下来的第二天就被兑现了：把前置改对之后补跑 VC-A02，**第一次执行就撞出一个 P0**（远程浏览器一律连不上网关，见本节开头 2026-09-03 那段）。缺陷已经在那儿躺了很久，挡住它的不是技术难度，是一行没人复核过的「需第二台真机」。
